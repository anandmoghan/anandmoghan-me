Platform plan: one site for family, ladder, materials and visitors

Spec for the coder agents. Written 2026-10-14. Owner: Anand.

Goals

  • One Next.js site (anandmoghan.me) hosts the blog, materials, and every app under /apps/*: family, ladder, wealth, expense, time, share, plus an admin panel.
  • One design: the family PWA's look (warm palette, Nunito Sans, cards, sticky header, bottom tab bar, per-domain accents) becomes the shared app design in ~/workspace/code/global/styles, used by the whole site.
  • One auth: every visitor gets a Firebase anonymous session; they can upgrade to Google or email, keeping their data; roles in Firestore drive app access and the admin panel.
  • One server folder: ~/workspace/code/anandmoghan-me-apis holds the Mac-side services (family bridge and worker, ladder worker).
  • No markdown as a source of truth for ladder or family: structured data in Firestore (or, for Mac-only private data, JSON on the Mac) and HTML for long text.

Hard rules for every agent

  • Never edit, move or delete anything in personal-manager, ladder, ladder-kavya or materials. Read and copy only.
  • The old systems keep running until cutover. New code must not run against the same queues or ports at the same time: the new bridge uses port 3201 (old: 3101) and stays stopped until cutover; new workers read new Firestore paths or are disabled by default.
  • Never read, print or commit secrets, .env* values, service accounts, data/, or health, fitness and parenting content.
  • Work in your own git worktree and branch; commit there with a clear message; do not push; do not deploy to the live site. Preview channels only (firebase hosting:channel:deploy <name>) when asked.
  • Shared files have one owner per phase (see below). Firestore rules are split into part files under firebase/rules/ and merged by scripts/merge-rules.mjs; edit only your own part.
  • Build must pass (npm run build, functions build, rules tests) before you report done.
  • No em dashes in UI copy. No @ts-ignore, no eslint-disable.

Ladder: recommended design

Ladder drops the local Next server and tunnel. Jobs, companies, notes and requests live in Firestore under ladder/{tracker} (anand, kavya), owner-only by role. The UI is a client app at /apps/ladder, so new roles appear the moment a worker writes them, with no rebuild or deploy. Buttons such as "prepare materials" or "refresh" write a request doc; the Mac worker listens with the admin SDK (the same pattern as the family bridge's request queue), runs the Claude agent loops headlessly, writes results back to Firestore, and uploads PDFs to Storage. Job descriptions are stored as sanitised HTML strings. This needs no inbound port on the Mac.

Data model and access

  • users/{uid}: profile (displayName, email, isAnonymous, createdAt, lastSeenAt, country). Owner read and write.
  • roles/{emailLowercase}: { admin: bool, apps: string[], ladderTrackers: string[] }. Admin read and write only. A function mirrors it into custom claims (admin, apps) on write and on sign-in; rules check claims plus email_verified.
  • Bootstrap: moghan.anand@gmail.com admin with all apps; the test user from .env.local (VITE_TEST_USER1_EMAIL) admin for tests. Seed with a script using the admin SDK, never in client code.
  • visits/{autoId}: uid, path, referrer, country, createdAt, session id. Written only by the api function (POST /api/visit), which reads the country from the request headers Firebase Hosting forwards; verify the header name and fall back to null. Admin read only. Recorded only after the visitor accepts analytics in the consent banner (UK PECR); anonymous sign-in itself is functional and needs no consent.
  • posts/{slug}/comments/{id}: uid, displayName, body (plain text, max 2000 chars), createdAt, status (visible or hidden). Any signed-in user, anonymous included, creates; author edits or deletes own; admin hides.
  • Family keeps family/household/** as today; access stays household membership, and admins with app family also pass.
  • Ladder: ladder/{tracker}/jobs/{slug}, companies/{slug}, requests/{id}; Storage ladder/{tracker}/generated/{slug}/*.pdf. Access: claim apps contains ladder and tracker listed for the user.

Anonymous to signed-in

On first visit the root layout signs in anonymously. Upgrading uses linkWithPopup (Google) or linkWithCredential (email), which keeps the same uid and therefore all data. If the Google or email account already exists (auth/credential-already-in-use), sign in to it and call POST /api/account/merge with the old anonymous ID token; the function copies the anonymous user's comments and prefs to the existing uid and deletes the anonymous user.
