Schedules that let a run keep going

A cosine schedule is a contract signed at launch. It fixes the total token count on day one, so a run that is going well cannot simply keep going, and a run that is going badly cannot be stopped at a useful point. Frontier runs have quietly dropped that contract. The learning rate now sits flat for most of training and decays late, and the batch size grows during the early phase instead of being fixed. Both changes make the schedule something a lab can adjust while the run is live.

Warmup-stable-decay

Warmup-stable-decay (WSD) has three phases: a short warmup, a long stable phase at the peak learning rate, and a decay at the end. MiniCPM popularised it for language models and found that a decay over about 10% of the tokens was enough, while 2.5% fell short [20]. The point is not a better final loss than cosine; it is that the run length no longer has to be known in advance. Any stable-phase checkpoint can be decayed to produce a finished model, and the main run carries on at peak.

The large reports all use some version of this shape. Kimi K2 held its learning rate constant at \( 2 \times 10^{-4} \) for 10T tokens, then decayed it by cosine over the remaining 5.5T [2]. DeepSeek-V3 stayed constant until 10T tokens and decayed over the next 4.3T before two short low-rate phases [16]. My read is that the long flat phase is also a monitoring window: the team watches a run whose dynamics do not change underneath it, and commits to a decay only once it trusts the checkpoint.

The trade-off is that stable-phase loss is not the real loss. A run at peak learning rate sits well above where it would land after a decay, and comparisons made before the decay can flip after it. Seeing the real number means running a cooldown branch: copy a checkpoint, decay it over a short stretch of tokens, evaluate, and throw the branch away. A cooldown can be started at any time, even retrospectively from a saved checkpoint, and the schedule scales as reliably as cosine [23]. Every branch still costs compute and is a short run with its own failure modes. Marin's 8B run saw its output head blow up during a deep cooldown; resetting the optimizer state and removing weight decay did not help; adding z-loss did [8]. The best peak learning rate for this schedule also sits below the cosine optimum [23], so a peak tuned for cosine is not a safe default.

Ramping the batch size

The batch size has the same problem at the other end of the run. Early in training the useful batch size is small: Merrill et al. measured the critical batch size of OLMo models directly and found it starts near zero, rises fast and then levels off [24]. A huge batch from step one spends tokens on updates that a much smaller batch would have made just as well.

Llama 3 405B started at 4M tokens per batch, doubled to 8M after 252M tokens and to 16M after 2.87T tokens [18]. Meta says the small early batch was there for stability, and the run had few loss spikes and needed no interventions for divergence. DeepSeek-V3 grew its batch fivefold, from 3,072 to 15,360, over the first 469B tokens and then held it [16].

A ramp is not free. Each step change alters the gradient noise and the number of tokens per optimizer step, so settings defined in steps (warmup length, the Adam \( \beta_2 \) averaging window) shift in token terms at every doubling. My read is that a spike right after a step change is hard to attribute, especially when the sequence length changes too, as it did at Llama 3's first doubling.
