Baseline: a streaming ASR → LLM → TTS voice agent

This is the baseline, the launch fallback and the comparison point for the target design in the previous section, a unified speech LLM with a downstream reasoning LLM. The target replaces the independent ASR and TTS models with one speech model and keeps the LLM behind a tool call; much of this section (transport, end-of-turn, chunking, barge-in, budget) carries over to it.

A cascaded voice agent is three models plus turn logic, run as overlapping streams. The latency comes from how well the stages overlap, not from any single model. Labels: Confirmed is sourced to a paper or first-party page, Reported is a self-reported figure from the vendor's or authors' own page, Inference is design opinion.

Component pipeline

This is the cascade of the earlier chapters with turn-taking added as an engineered heuristic. The text interface between stages carries no timing, so the pipeline cannot represent "the user is still talking" without the VAD and turn manager. That is the root of the trade-offs in the last subsection.

Transport

Use WebRTC between browser or phone client and server, with a data channel for control events. LiveKit and Pipecat are the two open frameworks that package this. Inference WebRTC gives you client-side echo cancellation, jitter buffering and congestion handling for free.

Budget the network as its own line. Wan-Streamer (arXiv 2606.25041) reports about 200 ms of model-side response latency and about 550 ms in total, including 350 ms of bidirectional network latency Reported. Time to first audio (TTFA), as used in this section, is the time from end of user speech to first agent audio at the client, so it includes that network time.

Between server components, use persistent bidirectional streams. A sensible pattern is a high-volume data plane (tokens, audio) plus a separate control plane for cancel, barge-in and feedback injection. REST is a poor fit because it has no native streaming and no clean channel for cancellation. Inference

VAD and end-of-turn detection

A bare VAD with a silence timeout is the half-duplex heuristic. It adds dead air to every turn, cannot tell a pause from a finished thought, and treats overlapping speech as noise.

The usual upgrade is a VAD that triggers a semantic end-of-turn model. Pipecat's Smart Turn is an open-source model that analyses the most recent 8 seconds of the user's turn, with a recommended VAD stop time of 0.2 s. The docs say inference can run "in under 100ms" on low-cost cloud instances. Reported (Pipecat docs, vendor numbers). LiveKit Agents documents an adaptive interruption mode that uses an audio model to distinguish real interruptions from backchannel acknowledgements. Reported (LiveKit docs).

Inference Treat the end-of-turn model as a latency lever, not just an accuracy one. A fast, aggressive endpoint gives a quick reply but cuts users off mid-thought. A conservative endpoint is safe but adds dead air. A learned detector shifts that curve; it does not remove it.

Streaming ASR: partials, finals and when to start the LLM

Streaming ASR emits partials (revisable) and finals (stable). The latency/WER trade-off is set by chunk size and lookahead. Confirmed examples: SpeechLLM-XL with 1.28 s chunks reports 2.7% / 6.7% WER on LibriSpeech test clean / other (arXiv 2410.03752); Qwen3-ASR's encoder uses an attention window of 1 to 8 s so one model serves streaming and offline (arXiv 2601.21337); Kyutai DSM treats ASR as a delayed text stream over audio (arXiv 2509.08753).

Inference: speculative start

Inference Never feed raw partials to the LLM; they change. Start the LLM when the end-of-turn candidate fires, using the current stable transcript. If the final transcript or a resumed user turn changes the text, cancel and restart. Skip speculation on long turns, which are likelier to change. Cost: wasted LLM (and, if enabled, TTS) compute on every cancel.

LiveKit ships a version of this: preemptive generation starts the LLM when a final transcript arrives, before the turn is confirmed. The docs list it as on by default, with preemptive TTS off, long utterances skipped (10 s default), and a retry cap of 3. They warn it does not always reduce latency, so check your metrics. Reported (LiveKit docs, read 2026-10-13; check your installed version).

LLM time-to-first-token levers

LLM time-to-first-token (TTFT) is plausibly the biggest single lever in the budget Inference. The levers below are standard serving techniques:

  • Prefix caching reuses KV for a shared system prompt. It needs identical token prefixes, so a prompt that changes per turn breaks the hit.
  • Chunked prefill stops one long prompt from inflating tail latency for other sessions.
  • Speculative decoding and quantization buy per-token speed; how hard to push is set by the budget.
  • Keep concurrency limits low enough that requests queue rather than slow each other.

Inference TTFT depends on load. Inworld reports about 27,000 aggregate tokens per second and a p50 TTFT around 1.7 s for Gemma 4 31B Dense on a B200 (Inworld guide, first-party measurement) Reported. A p50 of 1.7 s at that throughput is far above a voice-agent target, so tune for latency instead: a small model or router for simple turns, and a short reply style.

LLM text to TTS: chunking

Inference The default is sentence-level chunking: buffer LLM tokens until a sentence forms, then hand it to TTS. A sentence carries a full intonation contour, so it is a safe unit. Smaller chunks cut time to first audio but risk fragmenting prosody across the boundary. Make the first chunk small and cut at the first clause boundary (comma, dash, short sentence), with a minimum length so TTS has enough text to set intonation. Make later chunks full sentences; by then the first chunk's audio is hiding the wait.

FlashTTS replaces buffer-then-emit with a lagged multi-track autoregressive design for native streaming text input (arXiv 2606.09141) Reported.

Streaming TTS first packet

Pick TTS on first-audio latency at your real input lengths and concurrency. Reported first-packet figures are self-reports with different definitions, so do not compare across rows: Moshi 200 ms in practice, 160 ms in theory (arXiv 2410.00037), Qwen3-TTS 12 Hz 97 ms (arXiv 2601.15621), Kyutai DSM-TTS 150 ms at batch size 1 (arXiv 2509.08753), FlashTTS 325 ms first-packet latency (arXiv 2606.09141), Hume Octave about 200 ms in Instant Mode (Hume docs). Reported

Measure time to first byte, real-time factor, and p95/p99 under concurrent load, because a single median hides the tail Inference. Overlap stages inside the TTS server too. Inworld and Modular report that a streaming-aware scheduler returned the first 2 seconds of synthesized audio about 70% faster than a vanilla vLLM implementation (Modular case study). Reported

Barge-in

When VAD or the turn model detects user speech during agent speech, run these steps in order:

  1. Cancel the LLM stream and any queued TTS requests.
  2. Flush audio buffers on both server and client playout.
  3. Truncate the assistant turn in context to what was actually played, not what was generated.
  4. Return to listening and let ASR take the new input.

Step 3 matters because TTS runs faster than real time; the model "said" far more than the user heard. OpenAI's Realtime API exposes this as conversation.item.truncate with an audio_end_ms offset; it cuts the audio and removes the transcript for the unplayed portion Reported (OpenAI Realtime guide). Inference In your own stack, timestamp every audio chunk sent and track the client's playout position, then cut the text at the word boundary nearest that position.

Echo cancellation is the precondition. Without it the agent hears itself and interrupts itself. The W3C Media Capture and Streams spec defines an echoCancellation property that removes sound played by the speakers from the microphone recording Confirmed (W3C spec). Inference On telephony or server-side audio you must supply AEC yourself, or gate barge-in on a higher speech threshold while the agent talks. LiveKit adds false-interruption recovery: if no transcript follows within a window (2.0 s default), the agent can resume. Reported (LiveKit docs).

Failure modes and mitigations

Failure Mitigation Inference
Cuts the user off mid-thought Semantic end-of-turn model; longer stop time when the transcript looks incomplete
Dead air before replies Speculative LLM start; shorter VAD stop time; a short filler only if it fits the product
Agent hears itself and self-interrupts AEC; stricter barge-in threshold while speaking; false-interruption resume
Backchannel ("mm-hm") kills the reply Adaptive interruption mode; require minimum duration or words before cancelling
Context shows words the user never heard Truncate to played position, timestamped per chunk
ASR error propagates with no recovery The LLM sees only the transcript, so log ASR confidence and let the agent ask to confirm names and numbers
Prosody breaks at chunk seams Larger later chunks; 1-2 sentences of look-ahead
Tail latency under load Separate GPU pools per stage; cap concurrency; alert on p99 per stage

How to evaluate

  • Latency: per-stage and end-to-end p50/p95/p99 under production concurrency. Track TTFB for TTS and real-time factor.
  • ASR: WER on your own domain audio (names, numbers, accents), not only a public leaderboard.
  • TTS: an automatic MOS predictor (UTMOS) and resynthesis WER on every change, with human CMOS panels as periodic gates.
  • Interruption handling: stop latency after barge-in, false-interruption rate, and backchannel handling, scored with Full-Duplex-Bench v1 (arXiv 2503.04721) and v1.5 (arXiv 2507.23159). Those benchmarks cover pause handling, backchannel, turn-taking, interruption and overlap scenarios. Confirmed
  • Online: time-to-first-audio next to an engagement metric, since a fluent reply that arrives late reads as broken.

The cascade against the target design

A cascade is the right baseline and fallback: each stage is swappable, data is abundant and errors are attributable. Its structural limits are stacked latency, information loss at each text boundary, no recovery from ASR errors, and no natural interruption or backchannel handling Inference. Native full-duplex models (Moshi, dGSLM, arXiv 2203.16502) learn turn-taking from data, and state-head designs like Freeze-Omni (arXiv 2411.00774) and MinMo (arXiv 2501.06282) add a small decision module beside the LLM instead of using external heuristics. Confirmed

The cost of going native is data: real dual-channel conversation with genuine overlap is scarce (Fisher is about 2,000 h, arXiv 2410.00037), and the DuplexPO authors describe a tension between interactive dynamics and reasoning in full-duplex models (arXiv 2607.07148). Reported Inference The target keeps the cascade's separation of content from audio but folds ASR, turn-taking and TTS into one speech model, so the turn logic is learned, not engineered. The cascade stays as the launch fallback, the comparison point and a generator of synthetic dialogue.

In the interview, say:

"I treat a voice agent as overlapping streams with a turn manager on top. Latency is the overlap: speculative LLM start at end-of-turn, a small first TTS chunk, and barge-in that cancels everything and truncates context to what was played."
