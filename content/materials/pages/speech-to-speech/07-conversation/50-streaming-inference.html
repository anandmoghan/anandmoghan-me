Streaming inference engineering

A chat model answers a request and goes idle. A duplex voice model is a live loop: it must produce a frame every 80 ms for as long as the session lasts, even when nobody is talking. That changes what you optimise. The mean speed matters less than the worst frame, and memory per session matters more than weights.

How it works

KV growth. The KV cache from Streaming encoders stores a key and a value for every earlier position and layer, so each new frame appends to it. For the temporal transformer of the canonical model (32 layers, width 4096, full attention, bf16 storage), one frame costs:

\[ 2 \times 32 \times 4096 \times 2\ \text{B} = 524{,}288\ \text{B} \approx 512\ \text{KiB} \]

The first 2 is keys plus values and the last 2 is bytes per value, because bf16 is a 16-bit format that stores each value in 2 bytes. At 12.5 frames per second that is about 6.3 MiB per second, or about 23 GB for one hour. The small expansion transformer's cache can be dropped every frame. Grouped-query attention (GQA), which lets several attention heads share one set of keys and values, would shrink the figure. Inference

Session length. The cache grows linearly with time and with the number of sessions, so for many concurrent calls cache memory, not weights, sets capacity. The base model's paper states multi-turn behaviour over 5 minutes, so test past the reported context before promising more. Windowed attention is one fix: a streaming audio decoder uses 2 blocks of look-back and 1 of look-ahead. Windows forget the oldest audio, though, and newer ideas shrink the cache without forgetting. One proposal lets a side channel turn the speech it has already heard into a short text transcript during idle listening time, then evicts the old audio entries while keeping the transcript and the most recent audio. The authors report a peak cache 64.6% smaller on ten-minute sessions with comparable turn-taking and interruption behaviour. A separate result pools the cache entries of speech tokens to roughly text-level granularity and reports decoding at least 1.49 times faster, with quality on par with the uncompressed model. Both treat audio cache entries as more redundant than text. Inference

Batching sessions. A duplex session is always active, including in silence. Batching sessions into one GPU step raises throughput, but the whole batched step must still finish inside the frame slot. The sustainable batch is the largest \( B \) with

\[ t_{\text{step}}(B) < 80\ \text{ms} \]

Latency depends on load: one TTS model reports 150 ms at batch size 1 and about 380 ms at batch size 32.

Chunk size and the first packet. The chunk is the granularity after the stream starts, and the first packet (see Streaming a flow decoder) is the time until the first playable audio; they are different numbers. A chunked decoder needs a few tokens before it can emit anything, and any look-ahead it uses is added latency. A fully causal decoder pays none. Tool calls and the network are the other big items in a reply's delay; see Using tools while talking and, for the full latency budget, Latency and the baseline.

Levers and optimisations

Lever What it changes Trade-off
Chunk size Per-step cost against decision wait Shorter chunks cut the \( c/2 \) wait and pay the step cost more often; one ablation found 1.0 s better than 0.2 s or 0.1 s
Look-ahead in the decoder Quality of chunk joins Each block of look-ahead adds one block of delay
Predict several frames per wake How often the backbone runs One system reports about 1.5x deployment speed-up; the model must predict the future user too
Several audio tokens per pass Decoding steps per second of speech One system reports a 3 to 5x speed-up at 7B; an extra module to train
Quantisation Compute per frame One model reports RTF from 0.21 (INT4) to 0.27 (FP16) on a single GPU
Attention windowing or GQA Cache growth Bounds memory per session; early context can fade
Cache compression or text consolidation How much of the audio cache is kept One method reports a 64.6% smaller peak cache on ten-minute sessions; older audio is kept only as text and its fine detail is lost
Batch size Throughput against tail latency Bigger batches serve more calls and push the step toward its deadline

Quoted speed-ups are the authors' own, on different hardware and definitions; they are examples, not a ranking. The measurement side is in Evaluation and problems.

What goes wrong

  • Latency spikes. The mean looks fine and the 99th percentile frame is late, so the conversation stalls. Budget the tail.
  • Context loss. In a long session early turns fade, or a window drops an instruction. Test recall at turn \( N \), and watch GPU memory per hour.
  • Cold-start numbers. A first-packet figure at concurrency 1 will not hold at batch 32. State batch size, hardware and whether the run was cold.
  • Chunk joins. Short chunks lack information per window and degrade quality. Smaller is not automatically better.
In the interview, say:

"A duplex model has an 80 ms deadline every frame, silent or not. So I budget the worst frame, the KV cache per session and the decision wait, and I quote latency with its definition and load. Cache memory usually limits concurrency before compute does."
