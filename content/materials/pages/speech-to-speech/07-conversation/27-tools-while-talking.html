Using tools while talking

A voice agent that books a table, checks an order or searches the web must call a tool in the middle of a conversation. A tool call is often the slowest step in the whole reply, and silence on a phone line feels long. The question is how to keep the conversation alive while the tool runs.

Three tricks recur. Give the model a separate output channel for tool calls, so it can call a tool and keep talking. Guess the tool query before the user finishes the sentence. Run the tool in the background and let the voice cover the wait.

How it works

A parallel call channel. A voice model normally writes one text stream for what it says. One open model adds a second output stream that carries structured function calls, in parallel with the agent text. The same model listens, transcribes, reasons, calls tools and speaks inside one streaming system, so a call does not have to wait for the sentence to end.

Calling before the user finishes. Normal tool use waits for the full question. Streaming retrieval instead teaches the model when to issue a tool call during ongoing speech, and how to speak a summary that mixes the audio question with the text result. The tool query is predicted while the user is still talking, so the result is ready earlier. The authors report both better answer accuracy and a 20% lower tool-use latency on a spoken version of a retrieval benchmark.

Covering the wait. This is the tandem idea from Thinking while talking applied to tools: the opening words of a reply cost nothing extra, and the result is only needed when the sentence reaches it. Inference For a booking or a payment, the agent should confirm before acting; speculative queries suit read-only lookups.

What commercial APIs expose. Google's Gemini 3.8 Live model page makes asynchronous (non-blocking) function calling the default, keeps blocking as an option, and lists scheduling modes named silent, when-idle and interrupted for how a result is delivered. OpenAI's gpt-realtime-2 page lists function calling alongside a configurable reasoning effort, and warns that higher effort can increase latency.

Measuring it. Full-Duplex-Bench-v3 tests tool use under real speech: human recordings annotated for five disfluency categories, with tasks that chain several API calls. It compares six systems on accuracy, latency and turn-taking, and the headline is the trade-off. One commercial system was fastest at 4.25 s but took its turn only 78.0% of the time. The cascade had a perfect turn-taking rate and the highest latency at 10.12 s. One system led on first-try accuracy at 0.600, and it was not the fastest. The other conversation benchmarks are in Measuring conversation.

Levers and optimisations

Lever What it changes Trade-off
Call channel Whether a call can be emitted while the model speaks Lets the voice continue; adds an output stream to train and a structured format to get right
Speculative query Tool starts before the user finishes Hides latency; a wrong guess wastes a call, so suit it to read-only lookups Inference
Blocking against non-blocking calls Whether the model waits for the result Non-blocking keeps the conversation alive; the model must handle results that arrive mid-sentence
Result scheduling How a late result is delivered (one vendor lists silent, when-idle and interrupted modes) Interrupting is prompt and can cut the user off; waiting for idle can feel late Inference
Reasoning effort How long the model thinks before acting Higher effort can raise accuracy and, per the vendor, increases latency and output tokens
Retrieval method Which source supplies the facts Swappable in one system without retraining; the slowest source sets the wait

The levers are the vendors' and authors' own settings; apart from the reported 20% latency cut and the benchmark results, the trade-offs are design reasoning, not ablations. What goes wrong

  • Wrong tool, right voice. The open model above reports 82.5% tool-selection F1 on a tool-use benchmark, and says argument accuracy and end-to-end execution remain areas for improvement. Choosing a tool and filling in its arguments are different skills.
  • Real speech is messy. Across all systems in the benchmark, handling self-corrections and multi-step reasoning in hard scenarios were the most consistent failures. A speculative query launched before a self-correction would be wrong. Inference
  • Demo, not evaluation. Ask for tool accuracy, first-try pass rate and turn-take rate on messy audio, not a recorded success.
  • Unverified numbers. The gains reported for streaming retrieval and tandem retrieval come from the authors' own benchmarks. I found no source that compares them head to head.
In the interview, say:

"Tool latency is the longest step in a voice agent, so I overlap it with something else: guess the query while the user is speaking, run the call non-blocking, and let the opening words cover the wait. I would evaluate on messy real audio, because the failures there are self-corrections and chained calls, and I would report first-try accuracy next to turn-taking and latency."
