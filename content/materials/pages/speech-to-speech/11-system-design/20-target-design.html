The target design: a speech LLM that listens and speaks

The idea is a division of labour. One speech model owns everything that touches audio: hearing the user, deciding when to talk, and speaking. A separate text LLM owns content, and the speech model reaches it the way an agent calls a tool.

Think of a receptionist and an expert on the phone. The receptionist hears tone, knows when you have finished, says "one moment" while checking, and murmurs "mm-hm" while you explain. The expert never hears your voice; they get a short note and send back words.

Inference The overall design is my opinion. The component ideas have precedents, listed in the sources.

How it works

The listen head works first. A causal streaming encoder at 12.5 frames per second feeds a backbone initialised from a text LLM. Each frame the head emits streaming text (revisable partials and stable finals), paralinguistic tags (emotion, rate, language, confidence) and one action token that says what to do with the floor. It keeps ingesting the user stream while the agent speaks. The streaming parts are taught in Streaming encoders.

When the head decides the user is done, it makes the tool call: the stable transcript, the tags, the turn state (end-of-turn confidence, whether it interrupted a reply) and a pointer to what was actually played last. As in a cascade, start on the end-of-turn candidate and cancel if the user resumes. The downstream text LLM is any model with tools and retrieval. It streams text back with style cues such as emotion and pace, and because it never touches audio it can be swapped without retraining the speech model. Tool latency is covered in Tools while talking.

The speak head turns text chunks, style cues and a voice prompt into codec tokens at 12.5 frames per second, decoded by a causal codec decoder. A small first chunk cuts time to first audio; later chunks carry more lookahead for prosody. While the call runs it says a short filler, and the listen head can backchannel during long user turns without waiting for the LLM (see Thinking while talking).

Everything shares one clock. Every output chunk carries an absolute timestamp, as in Qwen3-Omni, which assigns one temporal ID per 80 ms. The renderer and client play audio on that clock and shed video frames first. This is what stops lip drift: if audio and video are paced by separate timers, a tiny speed difference adds up to a visible gap within minutes, but a player that lines chunks up by stamp can drop a late video block without pushing the picture behind the voice. Inference The drift is an illustration, not a measurement.

The speech LLM owns timing and the floor; the text LLM owns content. Who acts in each situation:

Situation What should happen Who acts
User pauses mid-turn Keep listening; end of turn from prosody and meaning, not silence Speech LLM
User finishes Fire the tool call early, since people start replying a touch before the other person ends (the floor-transfer offset in Turn-taking) Speech LLM decides; text LLM answers
Agent waits for the LLM Filler or acknowledgement while the call runs Speech LLM
Agent or user backchannels Agent says "mm-hm" at a prosodic boundary without taking the floor; a user "mm-hm", laugh or side talk does not stop the agent Speech LLM
Real barge-in Stop audio, flush buffers, truncate the reply to what was played, send played and heard text Speech LLM acts
After the interruption Resume the old thread or answer the new one Text LLM decides; speech LLM voices
Own voice in the mic Echo cancellation with the playback signal as an extra input Client and speech LLM

Levers and optimisations

Lever What it changes Trade-off
Where the duplex decision lives (an action token in the speech LLM, or a small module beside a frozen LLM) Who controls the floor; how learned the turn-taking is An action token needs dual-channel data; a side module is cheaper but less integrated
Decision cadence (per 80 ms frame, 160 to 240 ms chunk, 1 s chunk) Timing resolution of end of turn, yield and backchannel A chunk waits half its length on average (Conversation clock); per-frame decisions cost compute
Interface to the LLM (transcript, plus tags and turn state) How much emotion and turn context the LLM can use Calibrate tags; a swappable LLM may ignore them
Speak-chunk sizes (small first, larger later) Time to first audio versus prosody at the seams Smaller first chunk risks fragmented intonation
Codec and token rate (causal residual quantiser at 12.5 Hz, or lower or higher) Expressiveness versus sequence length Expressive voice needs acoustic codebooks; lower rates lose detail
Model sizes (speech backbone versus text LLM) Per-frame deadline versus reasoning quality The speech model must finish every 80 ms frame; the LLM is a normal streaming text service

What goes wrong

  • Lost paralinguistics. Emotion and uncertainty must be flattened into tags. If the tags are missing or miscalibrated, the LLM answers as if the user were neutral.
  • Backchannel kills the reply. Teams catch it with false-yield rate per minute and by scoring with Full-Duplex-Bench (see Measuring conversation).
  • Context shows words the user never heard. TTS runs faster than real time, so truncate the reply to the played position using per-chunk timestamps.
  • Forgetting. Speech input erodes LLM knowledge, which is why the downstream LLM stays untouched and the speech backbone is gated at every stage on ASR WER, text QA and timing.
  • Reward hacking. Monotone prosody, or an agent that never yields (see Reward hacking guards).
In the interview, say:

"One speech LLM listens and speaks on a 12.5 Hz clock: streaming text with emotion tags, an action token for turn-taking, backchannels and barge-in, and expressive TTS. It calls a text LLM for content, so tools and safety stay in text, and a filler covers the extra hop."
